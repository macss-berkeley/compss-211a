Counting rows vs. counting recorded values

For all six requests:

  • COUNT(*) / len(requests): 6 rows.
  • COUNT(hours_to_close) / requests["hours_to_close"].count(): 4 recorded durations.

B’s 0 is a recorded value, so it counts. C and F have no duration. A median would use only the four recorded values, so it would not describe all six requests.

Using this in the notebook

When you compare two results, check every group and every request ID. One row that looks right is not enough. Decide how missing values should be handled, and write that into your code. Before a join, check that each key appears only once in the lookup table. For any number you report, look at which rows went into it.

In pandas, add validate="many_to_one" to the merge. It raises an error if a lookup key appears more than once. In SQL, you have to check for repeated keys yourself, for example:

SELECT district, COUNT(*) AS rows_per_key
FROM districts
GROUP BY district
HAVING COUNT(*) > 1;

This page only shows results for the examples above. To write and run your own queries, use the Week 5 notebook. Two more things to know. If you change how pandas stores missing values (the column’s dtype), comparisons like != can behave differently. And pandas will match a missing join key to another missing key, but SQL never treats two NULLs as equal. Our lookup table has no missing keys, so that does not come up here.
